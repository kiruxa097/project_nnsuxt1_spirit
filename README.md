# MVP оркестратора процессов оценки рисков

Проект содержит React/Vite интерфейс и FastAPI-сервис оркестрации. Backend хранит запуски, проверяет зависимости, распределяет задачи по очереди и управляет блокировками ресурсов в PostgreSQL.

> **Граница текущего MVP:** оркестратор управляет допуском задач (CREATED/QUEUED/RUNNING), блокировками и журналом решений. В архиве нет worker/исполнителей самих BP-01…BP-04: статус RUNNING означает, что задача допущена оркестратором, а не что выполнен банковский расчёт. Для реального бизнес-результата нужен адаптер/worker, который вызовет внутренний `finish_execution()` после выполнения процесса. Данные тестовые, не подключайте реальные банковские источники.

## Состав

- `frontend/` — React 19, TypeScript, Vite, React Router, Axios.
- `backend/` — FastAPI, SQLAlchemy 2, PostgreSQL.
- `docs/` — описание процессов, схемы БД и OpenAPI-контракт.
- `docker-compose.yml` — PostgreSQL для локальной разработки.

## Быстрый запуск

Требования: Python 3.11+, Node.js 20.19+ (или 22.12+), npm, Docker Desktop.

1. Запустите PostgreSQL:

   ```bash
   docker compose up -d db
   ```

2. Создайте виртуальное окружение и установите backend:

   ```bash
   cd backend
   python -m venv .venv
   # Windows PowerShell:
   .venv\Scripts\Activate.ps1
   # macOS/Linux:
   source .venv/bin/activate
   pip install -r requirements.txt
   ```

3. Инициализируйте схему и тестовые данные (из папки `backend/`):

   ```bash
   python -m app.db.seed
   ```

   Команда создаёт таблицы, реестр процессов/ресурсов и синтетический набор (1000 клиентов, 3000 кредитов, заявки и платежи). Повторный запуск пропускает генерацию, если клиентские данные уже присутствуют.

4. Запустите API в первом терминале (из `backend/`):

   ```bash
   uvicorn app.main:app --reload --host 0.0.0.0 --port 8000
   ```

   Проверка: http://localhost:8000/health  
   Swagger: http://localhost:8000/docs

5. Запустите frontend во втором терминале:

   ```bash
   cd frontend
   npm ci
   npm run dev
   ```

   Откройте адрес Vite, обычно http://localhost:5173. Vite проксирует `/api` на `http://127.0.0.1:8000`.

## Конфигурация

По умолчанию backend использует:

`postgresql+psycopg://postgres:postgres@localhost:5432/credit_risk_db`

Переопределить можно переменной окружения `DATABASE_URL`. Для локальной разработки можно скопировать `.env.example` в `.env` и экспортировать переменную в окружение перед запуском backend. Сам FastAPI не загружает `.env` автоматически.

## Как работает запуск

1. Пользователь выбирает процесс и заполняет параметры.
2. Frontend отправляет `POST /executions` с `process_id`, `params`, `priority`.
3. Backend проверяет наличие процесса и обязательных параметров, вычисляет ключ идемпотентности.
4. Сервис проверяет зависимости процесса.
5. По матрице `read_resources`/`write_resources` формируются запросы блокировок. Для одного ресурса READ совместим с READ; WRITE конфликтует с READ и WRITE.
6. Разделяемые ресурсы блокируются по партициям (например, дате или клиенту). `ALL` пересекается с любой партицией.
7. Если допуск возможен, задача получает RUNNING и захватывает lease-блокировки; иначе получает QUEUED с причиной и ID блокирующего запуска.
8. После завершения/отмены блокировки освобождаются и очередь повторно проверяется.
9. Все ключевые решения записываются в `execution_logs`.

## Основные API

- `GET /processes` — реестр бизнес-процессов.
- `POST /executions` — создать запуск.
- `GET /executions` и `GET /executions/{id}` — список и карточка запуска.
- `POST /executions/{id}/cancel` — отмена.
- `PATCH /executions/{id}/priority` — смена приоритета CREATED/QUEUED.
- `GET /executions/{id}/logs` — журнал событий.
- `GET /queue` — очередь.
- `GET /locks` — активные блокировки и ожидающие задачи.
- `GET /health` — health-check.

Приоритеты: `1` — CRITICAL (наивысший), `2` — HIGH, `3` — MEDIUM, `4` — NORMAL, `5` — LOW.

## Ограничения и следующий этап

- Нет аутентификации/авторизации и разграничения ролей.
- Нет worker-пула, брокера сообщений и фактического выполнения BP-алгоритмов.
- Нет миграций Alembic: `create_all()` подходит для чистого MVP, но не для безопасного обновления существующей БД.
- Lease-блокировки требуют регулярного heartbeat/очистки просроченных lease в production.
- Нет полноценного отчётного API; экран результатов показывает запуски, а не финансовые агрегаты.
- Перед production нужны интеграционные и конкурентные тесты PostgreSQL, мониторинг, секреты из vault/env, аудит доступа и резервное копирование.
