# Архитектура и взаимодействие

## Компоненты

### Frontend
React SPA. `src/api/client.ts` — единый Axios-клиент с base URL `/api`. `src/api/runs.ts` и `src/api/processes.ts` обслуживают каталог процессов, дашборд и создание запусков. `src/front2/api.ts` адаптирует backend DTO к UI-модели очереди, блокировок, истории и карточки запуска. В `vite.config.ts` запросы `/api/*` перенаправляются на FastAPI с удалением `/api`.

### Backend
FastAPI предоставляет HTTP API. `api/endpoints.py` валидирует входные DTO и сериализует Task. `services/orchestrator.py` выполняет admission control, вычисляет идемпотентность, проверяет ресурсы, ставит задачу в очередь, захватывает/освобождает блокировки и пишет аудит. `services/dependencies.py` проверяет зависимости. `db/models.py` описывает SQLAlchemy-модели.

### PostgreSQL
Хранит реестр процессов/ресурсов, запуски, запросы ресурсов, lease-блокировки, зависимости и журнал событий. Синтетические бизнес-данные лежат в таблицах клиентов, заявок, кредитов, платежей и результатов риска.

## Контракт UI ↔ API

| Действие UI | HTTP | Ответ / назначение |
|---|---|---|
| Каталог | `GET /processes` | `id`, `code`, `name`, `description`, `duplicate_policy` |
| Создание | `POST /executions` | `process_id`, `params`, `priority`; ответ содержит `id`, `status`, `params`, `priority`, `decision_reason` |
| Очередь/история | `GET /executions`, `GET /queue` | DTO запуска и позиция очереди |
| Карточка | `GET /executions/{id}` | поля запуска и блокирующая задача |
| Журнал | `GET /executions/{id}/logs` | `time`, `level`, `message` |
| Отмена | `POST /executions/{id}/cancel` | новый статус |
| Приоритет | `PATCH /executions/{id}/priority` | приоритет 1…5 |
| Блокировки | `GET /locks` | ресурс, партиция, владелец, режим, ожидающие |

Frontend преобразует snake_case API-поля в camelCase UI-модель в `front2/api.ts`. Не следует использовать UI-типы напрямую как backend-схемы.

## Статусы

- `CREATED` — создана.
- `QUEUED` — ожидает зависимости, ресурс или лимит параллелизма.
- `RUNNING` — оркестратор допустил задачу и выдал блокировки.
- `COMPLETED` — worker подтвердил успех (в текущем комплекте worker отсутствует).
- `FAILED` — ошибка процесса/зависимости.
- `CANCELLED` — отменена пользователем.

## Правила блокировок

Для одного ресурса запросы READ/READ совместимы. Если хотя бы одна сторона WRITE — доступ конфликтует. `partition_key` ограничивает область данных: одинаковые ключи и `ALL` конфликтуют, разные конкретные ключи могут выполняться параллельно. Для предотвращения дедлоков строки ресурсов блокируются в стабильном порядке по ID.

## Важное замечание о бизнес-зависимостях

Спецификации зависимостей находятся в `Process.dependencies`. Логика отдельных связей BP-01/BP-02 и BP-04/BP-03 реализована в `dependencies.py`. Перед подключением реальных исполнителей нужно согласовать, как подтверждается синхронизация `PAYMENTS_SYNC` и как worker сообщает результат оркестратору.
